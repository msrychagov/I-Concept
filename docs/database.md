# PostgreSQL: запуск и перенос данных

## Запуск

Скопируйте `.env.example` в `.env`, задайте свои `DB_PASSWORD` и `VUC_ADMIN_PASSWORD`:

```sh
cp .env.example .env
docker compose up --build -d
docker compose logs migrate app
```

PostgreSQL 17 хранит данные в томе `postgres_data`. Сервис `migrate` ждёт готовности
БД, применяет SQL из `internal/migrations/sql` и завершается. Приложение запускается
только после успешной миграции. При отсутствии или изменении применённой миграции
приложение отказывается запускаться. Ошибка подключения не переключает его на JSON.
Демоданные автоматически не создаются.

Приложение доступно на `http://localhost:8080`. `APP_PORT` меняет внешний порт.
PostgreSQL опубликован только на localhost; `POSTGRES_PORT` меняет его внешний порт.
Пароли в `.env` не попадают в Git и Docker-образ. Не удаляйте рабочий том через
`docker compose down -v`, если данные нужно сохранить.

## Перенос существующего JSON

Остановите прежний сервер, который записывает JSON, и сохраните копию его файла.
Запустите новую БД и мигратор, затем выполните:

```sh
./scripts/import-data.sh ./data/vuc.json
```

Импорт работает только с пустыми рабочими таблицами, в одной транзакции. Исходный
файл монтируется только для чтения. При ошибке, неизвестном JSON-поле, нарушении
ограничений или наличии данных импорт отклоняется. Исправлять несовместимые данные
нужно в копии файла; исходник команда не меняет. Сохраняются ID, хеши паролей,
приглашения, сеансы входа, ответы, версии и ревизии. Для старых записей без владельца
применяются прежние правила: единственный преподаватель получает записи, при
неоднозначности они остаются закрытыми. Существующие имена ВУЦ автоматически
в справочник не добавляются — это действие администратора.

После импорта можно запускать приложение и создавать ВУЦ/приглашения:

```sh
docker compose exec app vuc -create-vuc 'ВУЦ при университете'
docker compose exec app vuc -invite-teacher teacher@example.ru -vuc 'ВУЦ при университете'
```

В режиме PostgreSQL эти команды могут работать одновременно с сервером.

## Демоданные

Для отдельной пустой тестовой БД:

```sh
./scripts/seed-demo.sh
```

Создаются один ВУЦ, преподаватель, девять студентов, три взвода, два шаблона,
четыре назначения, начатые и завершённые тесты и автобиографии.

| Роль | Логин | Пароль |
| --- | --- | --- |
| Преподаватель | `teacher@example.test` | `TeacherDemo2026!` |
| Студенты | `student1@example.test` … `student9@example.test` | `StudentDemo2026!` |

Повторный запуск seed отклоняется без изменения данных. Импорт и seed — альтернативы
для заполнения пустой БД. Существующая команда `vuc -demo-reset` намеренно заменяет
все рабочие данные; в SQL-режиме предыдущий снимок сохраняется в
`repository_backups` в той же транзакции. Используйте её только для сброса демосреды.

## Запуск без Docker

Настройте `DATABASE_URL` вида `postgres://USER:PASSWORD@HOST:5432/DB?sslmode=require`
или переменные `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_SSLMODE`.
`DATABASE_URL` имеет приоритет. Для локального PostgreSQL без TLS явно укажите
`sslmode=disable`. Пароль с особыми символами в URL нужно URL-кодировать; вариант
с отдельными переменными делает это автоматически.

```sh
go run ./cmd/migrate
go run ./cmd/importdata -file ./data/vuc.json  # либо go run ./cmd/seed
go run ./cmd/vuc
```

Если ни `DATABASE_URL`, ни `DB_HOST` не заданы, сохраняется прежний локальный
режим `-data data/vuc.json`. Команды migrate, seed и importdata требуют PostgreSQL.
Compose всегда использует PostgreSQL; флаг `-data` в нём не выбирает хранилище.

## Устройство хранения

- `internal/platform/database`: конфигурация и пул подключений pgx.
- `internal/migrations`: встроенные SQL-файлы, проверка контрольных сумм,
  транзакционное применение под advisory lock, таблица `schema_migrations`.
- `internal/repository/postgres`: репозиторий, согласованное чтение и транзакции.
  Организации, аккаунты и учебные данные разнесены по файлам. Общий типизированный
  механизм чтения и синхронизации строк находится в `records.go`.
- `cmd/migrate`, `cmd/seed`, `cmd/importdata`: отдельные административные команды.

Отдельные таблицы: `vucs`, `platoons`, `accounts`, `logins`, `invitations`,
`profiles`, `assignments`, `sessions`, `form_submissions`. Одна сущность — одна
строка с JSONB-полями, индексами, проверками уникальности и внешними ключами.
Изменённые строки обновляются через upsert, удалённые — удаляются; вся таблица
при каждом сохранении не перезаписывается. Архивные сессии могут ссылаться на
ID студента/назначения из другой установки, поэтому эти два поля индексированы,
но не имеют внешнего ключа. Связи с ВУЦ пока сохраняют прежние имена; существование
ВУЦ и права изменения проверяет слой сценариев приложения.

Банки вопросов, методика, справочники и описания фиксированных анкет остаются
в JSON в `internal/questionbank` и `internal/formbank`, встроенных в бинарник.
Пользовательские шаблоны и снимки вопросов в назначениях/сессиях сохраняются в БД:
они фиксируют то, что реально проходил студент, и не заменяются при обновлении банка.

Интерфейс сценариев пока работает с полным согласованным снимком: чтение выполняется
в REPEATABLE READ, запись — под общей транзакционной блокировкой до чтения данных.
Это сохраняет прежнюю семантику сценариев и исключает потерю изменений между
процессами приложения, но стоимость чтения растёт с объёмом данных, а записи
сериализуются. Для больших установок следующий шаг — отдельные SQL-запросы по
владельцу/назначению и пагинация вместо загрузки всего снимка. Обходить репозиторий
прямыми конкурентными SQL-записями нельзя: они не используют его блокировку.

Новые изменения схемы оформляются новым `NNN_name.up.sql`; уже применённые файлы
менять нельзя. Мигратор применяет только up-миграции. `001_initial.down.sql` —
разрушительный SQL для ручного отката пустой тестовой схемы, автоматически не запускается.

## Резервная копия и проверка

`repository_backups` помогает при явном демосбросе, но не заменяет отдельную копию БД:

```sh
docker compose exec -T postgres pg_dump -U app -d app_db -Fc > backup.dump
# Восстановление в заранее созданную пустую БД:
docker compose exec -T postgres pg_restore -U app -d app_db --no-owner < backup.dump
```

Копии содержат персональные данные и хеши учётных данных; храните их с ограниченным
доступом, отдельно от рабочего тома.

```sh
go test ./...
TEST_DATABASE_URL='postgres://USER:PASSWORD@localhost:5432/TEST_DB?sslmode=disable' \
  go test ./internal/repository/postgres -v -count=1
```

Интеграционная проверка создаёт собственную временную схему и удаляет только её.
Проверяются повторные миграции, все виды записей, откат при ошибке, внешние ключи,
параллельные изменения, резервная копия, импорт и защита непустой БД от перезаписи.
